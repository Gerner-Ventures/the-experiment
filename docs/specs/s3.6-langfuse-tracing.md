# S3.6 — Agent Tracing & Observability with Langfuse

Add structured LLM tracing and observability to the simulation backend using Langfuse, providing per-experiment, per-round, per-agent visibility into every LLM call with cost tracking, prompt inspection, and latency analysis.

## Background

The backend makes LLM calls across three roles — GM planning, agent decisions, and memory operations — routed through litellm. Today, usage is tracked in-memory via `UsageTracker` (a list of `UsageRecord` objects) with no persistence, no trace hierarchy, and no way to inspect prompts/responses after a run. As experiments scale to more agents and rounds, we need durable, queryable observability into what the LLM layer is doing and how much it costs.

Langfuse provides trace/span/generation hierarchy, prompt versioning, cost tracking, and a dashboard — all of which map cleanly onto the simulation's round-based lifecycle.

## Requirements

### 1. litellm Callback Integration

Use litellm's native Langfuse callback to automatically capture all LLM completions.

**Acceptance Criteria:**
- [x] `langfuse` added to backend dependencies
- [x] Langfuse callback registered on the litellm Router via `success_callback` and `failure_callback`
- [x] All LLM calls (gm, agent, memory roles) appear as generations in Langfuse without changes to calling code
- [x] Token counts and cost estimates propagated to Langfuse from litellm's response

### 2. Trace Hierarchy

Create explicit traces and spans that map to the simulation lifecycle.

**Acceptance Criteria:**
- [x] Each `run_round()` call creates a Langfuse **trace** named `round-{round_number}` with `session_id` set to the `experiment_id`
- [x] Each simulation phase (gm_plan, dawn, morning, midday, afternoon, night) creates a **span** under the round trace
- [x] Each LLM call is linked to its parent span via `trace_id` and `parent_observation_id` passed through `LLMRequest.metadata`
- [ ] Agent decision spans include `agent_id` and `agent_name` as metadata
- [ ] Memory operation spans (classify, consolidate, relationship) are nested under the night phase span

### 3. Configuration

Langfuse credentials and behavior controlled via environment variables and Settings.

**Acceptance Criteria:**
- [x] `Settings` model extended with `langfuse_public_key`, `langfuse_secret_key`, `langfuse_host` (all optional, defaulting to `None`)
- [x] `langfuse_enabled` derived property: `True` when both keys are set
- [x] Langfuse tracing is a no-op when credentials are not configured (no errors, no performance impact)
- [ ] K8s deployment updated with Langfuse env vars sourced from a Secret

### 4. Metadata Enrichment

Enrich Langfuse traces with simulation-specific metadata for filtering and analysis.

**Acceptance Criteria:**
- [x] Traces tagged with `experiment_id`, `round_number`, `total_rounds`
- [x] Generations tagged with `role` (gm/agent/memory), `model`, `agent_id` (when applicable)
- [ ] Failed/repaired JSON parsing attempts logged as span events
- [ ] Experiment status (running/completed/collapsed) set as trace metadata on round completion

### 5. Graceful Lifecycle

Ensure Langfuse SDK flushes data reliably without blocking the simulation.

**Acceptance Criteria:**
- [x] Langfuse client initialized once at app startup (singleton via Settings/dependency injection)
- [x] `langfuse.flush()` called on application shutdown (FastAPI lifespan)
- [x] Tracing errors are logged but never propagate to the simulation (fire-and-forget)

## Technical Design

### Architecture

```
SimulationEngine.run_round()
  |-- creates Langfuse Trace (session_id=experiment_id)
  |
  |-- gm_plan phase  --> Span
  |     |-- LLMClient.generate_structured() --> Generation (auto via litellm callback)
  |
  |-- morning phase  --> Span
  |     |-- per-agent decision --> child Span
  |           |-- generate_structured() --> Generation
  |
  |-- midday phase   --> Span (no LLM calls, social/meeting logic)
  |
  |-- afternoon phase --> Span
  |     |-- per-agent decision --> child Span
  |           |-- generate_structured() --> Generation
  |
  |-- night phase    --> Span
        |-- per-agent reflection --> child Span
              |-- memory classify  --> Generation
              |-- memory consolidate --> Generation
              |-- relationship consolidate --> Generation
```

### Integration Points

1. **`LLMClient.__init__`** — Register `langfuse` in litellm callback list when enabled
2. **`LLMClient.generate_structured`** — Inject `trace_id`, `parent_observation_id`, `generation_name` into `metadata` dict (litellm forwards these to the Langfuse callback)
3. **`SimulationEngine.run_round`** — Create trace, pass trace context down through service calls
4. **`SimulationEngine._action_phase`** / **`_night_phase`** — Create spans per phase and per agent
5. **`app/main.py`** lifespan — Init and flush Langfuse client

### New Files

- `backend/app/core/langfuse.py` — Langfuse client singleton, trace/span helpers
- No new dependencies beyond `langfuse` (litellm already supports it natively)

### Context Propagation

The existing `metadata: dict` on `LLMRequest` is the propagation mechanism. Today it carries `experiment_id`, `agent_id`, `round_number`. We add:

```python
metadata = {
    # existing
    "experiment_id": "...",
    "agent_id": "...",
    "round_number": 5,
    # new — Langfuse context
    "trace_id": "langfuse-trace-uuid",
    "parent_observation_id": "langfuse-span-uuid",
    "generation_name": "agent-decision",
    "tags": ["agent", "morning"],
}
```

litellm's Langfuse callback reads `trace_id` and `parent_observation_id` from metadata automatically.
